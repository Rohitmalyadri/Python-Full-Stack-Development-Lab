> *"Every click, every search, and every login begins with a conversation between a client and a server."*

---

# Overview

Every modern application—whether it's YouTube, Instagram, Amazon, or ChatGPT—follows the Client–Server Architecture.

Whenever you click a button, submit a form, or refresh a page, your device communicates with another computer somewhere in the world. Understanding this communication is one of the most important concepts in Full Stack Development.

This module explains how clients and servers interact, how requests and responses flow, and why this architecture became the foundation of modern software.

# Why Learn Client–Server Architecture?

Imagine building a shopping application.

Questions arise immediately:

* Where are the products stored?
* Where is user information saved?
* Who verifies the password?
* How is payment processed?
* How are orders tracked?

The browser alone cannot perform these tasks.

This is where the server comes in.

---

# What is a Client?

A **Client** is any device or application that requests a service from another computer.

Examples:

* Google Chrome
* Firefox
* Microsoft Edge
* Mobile Applications
* Desktop Applications

The client's responsibility is to:

* Display information
* Collect user input
* Send requests
* Show responses

Think of the client as the **customer** in a restaurant.

---

# What is a Server?

A **Server** is a computer or software application that receives requests, processes them, and returns responses.

A server can:

* Authenticate users
* Process business logic
* Access databases
* Store files
* Return API responses
* Handle multiple users simultaneously

Think of the server as the **chef** in a restaurant.

---

# Restaurant Analogy

Imagine ordering food.

Customer → Client

Waiter → HTTP Request

Kitchen → Server

Chef → Business Logic

Storage Room → Database

Prepared Food → HTTP Response

The customer never enters the kitchen.

Similarly, the browser never directly accesses the database.

---

# Client–Server Architecture

```text
                Client
          (Browser / Mobile App)
                    │
              HTTP Request
                    │
                    ▼
                Web Server
                    │
          Business Logic Layer
                    │
                    ▼
                Database
                    │
          Retrieve / Store Data
                    │
                    ▼
              HTTP Response
                    │
                    ▼
                Client
```

---

# Request–Response Cycle

Every interaction follows the same cycle.

### Step 1

User performs an action.

Example:

Clicks the Login button.

---

### Step 2

The browser creates an HTTP Request.

Example:

```http
POST /login
```

---

### Step 3

The server receives the request.

The backend application checks:

* Is the request valid?
* Is the user registered?
* Is the password correct?

---

### Step 4

The server communicates with the database.

Example:

```text
SELECT * FROM users
WHERE email='rohit@example.com'
```

---

### Step 5

The database returns the result.

---

### Step 6

The server prepares an HTTP Response.

Example:

```json
{
    "message": "Login Successful",
    "token": "JWT_TOKEN"
}
```

---

### Step 7

The browser displays the result.

The user sees:

> Welcome Rohit!

# Why Doesn't the Browser Access the Database Directly?

Imagine anyone could connect directly to your bank's database.

What could happen?

* Password theft
* Data modification
* Account deletion
* Security breaches

Instead:

```text
Browser
   │
Backend
   │
Database
```

The backend acts as a security layer.

It verifies permissions before allowing database access.


↓

### Backend

Processes:

* Search Query

↓

### Database

Returns matching products.

↓

### Backend

Formats the response.

↓

Displays product cards.

# Benefits of Client–Server Architecture

* Better Security
* Centralized Data
* Easy Maintenance
* Scalability
* Multiple Clients Can Use the Same Backend
* Easier Updates
* Separation of Responsibilities

---

# Limitations

* Requires Network Communication
* Server Downtime Affects Users
* Higher Infrastructure Cost
* Backend Development Adds Complexity

---

# Where FastAPI Fits

Throughout this lab, FastAPI will act as our **Backend Server**.

```text
React Frontend
       │
 REST API
       │
FastAPI Backend
       │
PostgreSQL Database
```

Everything you build later—authentication, CRUD operations, file uploads, APIs—will follow this architecture.

---

# Key Takeaways

* A client requests services; a server provides them.
* Modern web applications use the Request–Response model.
* Browsers should never communicate directly with databases.
* Backend servers enforce security and business rules.
* FastAPI acts as the backend layer in a Python Full Stack application.
